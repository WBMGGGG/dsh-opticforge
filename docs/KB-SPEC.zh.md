# 知识库改写规范 v2（原文型板块 A–E）

> 适用范围：A01–E01 九个有厂商原文快照的板块。
> 编译型板块（F/G/H/I）没有单一原文，规则见 `docs/KB-SPEC-COMPILED.zh.md`。
> 板块与条目清单见 `docs/KB-OUTLINE.zh.md`；本规范只管"怎么把原文改写成事实条目"。

公开仓库不能放厂商原文。全部 knowledge chunk 改写成"事实条目"：只保留可核验的事实、数值、判据、边界，不保留原文措辞。

## 一、目录结构

```
_kb-raw/<doc>.json      原文快照（私有，.gitignore，只给维护者复核）
data/kb/<doc>.json      改写后的事实条目（公开，源文件）
data/kb-data.json       构建产物，不要手改
data/kb-meta.json       版本/计数/覆盖清单，构建时自动更新
```

## 二、条目字段（9 个，与运行时契约一致，不得增删）

| 字段 | 要求 |
|---|---|
| `doc_id` | 原样 |
| `chunk_id` | 原样，一一对应，绝不变更（这是引用锚点） |
| `status` | 原样（present / missing_source / substitute） |
| `is_original_excerpt` | 一律 `false` |
| `text` | 改写后的事实条目，见第三节 |
| `source` | 原样复制 |
| `page_or_section` | 原样复制 |
| `keywords_zh` | 保留原关键词，可补充正文出现的新术语，空格分隔 |
| `disclaimer` | 原样 |

## 三、text 写法

第一行：`【标题】`，标题是检索锚点，必须含型号或主题 + 关键参数名。

之后每行一条 `字段：值`，一行一个维度。

```
【IFS2402 规格（量程 0.5 / 1.5 / 3.5 mm 三档）】
量程：0.5 / 1.5 / 3.5 mm
静态分辨率：< 8 / < 30 / < 50 nm
线性度：±0.15 / ±0.60 / ±1.40 µm
```

规则：

1. 多档位用 ` / ` 分隔，标题里注明列序对应哪些型号，否则读数会错位。
2. 数值保留原始精度，不四舍五入、不换算单位。
3. 原文的括号注释（测试条件、脚注）要保留，它是数值的适用边界。
4. 纯叙述类块（原理、流程）写成连续的"方式/判据/适用"短句，不硬拆成表格。
5. 长度只设下限 120 字，**不设上限**。完整性优先：原文有的判据、数值、适用条件、边界都要写进去，不许为了凑字数或压长度删事实。内容多就照实写长，不要硬塞；当前一条原文块对应一条条目（校验器要求 chunk_id 集合与原文严格相等）。若确实需要拆条，要先扩展 chunk_id 契约（如 `C02-07a`）并同步改校验器与基线，属契约变更，当前版本不含此能力。

## 四、硬规则

1. **每个数字必须能在同 chunk 的原文里找到**（构建脚本逐字校验，包括千分位写法：原文写 `2,048` 就写 `2,048`，不能写 `2048`）。
2. 不写营销词：low cost、high performance、领先、优异、完美。
3. 不跨 chunk 合并事实；一个条目只覆盖一个 chunk。
4. 不推断。原文只说 A，就只写 A；原文没给的条件不补。
5. 中文为主；型号、参数名、标准号保留英文/原文。
6. 原文没有可用事实的（如缺原文的块），`text` 写清"缺什么、为什么缺"，不要编造。

## 五、自检

```powershell
node scripts/build-kb.mjs --doc A01
```

逐块报告：字段缺失、数字对不上、过短（<120 字）。全绿再合入。

长度不设上限：**完整性优先**。原文有的判据、数值、适用条件、边界都要写进去；内容多就照实写长，不许为了字数删事实。超过 2000 字时校验器只打印提示，不判失败。拆条受 chunk_id 契约限制，见第三节第 5 条。

## 六、样板

`data/kb/A01.json` 的 `A01-02`（规格表改写）与 `A01-01`（原理叙述改写）是两份样板，照它们的粒度写。
